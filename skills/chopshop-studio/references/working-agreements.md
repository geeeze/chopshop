# Working agreements (process)

> The behavioural rules. The two shortest always-on ones also sit in `SKILL.md`.

- **Do not restart Puma (or checkout/commit) while a subagent holds the working tree on a feature branch.** The subagent edits the SAME `~/chopshop-studio` checkout; restarting boots its half-committed code (models eager-load at boot, views compile lazily) and a concurrent `git checkout`/commit races its uncommitted changes. Apply the DB migration (a separate concern) freely, but hold the restart until the subagent commits and you merge to `main` — one restart clears both the schema drift and deploys the subagent's work together.
- **A write to `AGENTS.md` is APPROVAL-GATED, not forbidden — and the approval is answered in the UI, not in chat.** The protected-agent-instruction-file guard raises a prompt owned by the interface; typing "approve it" as a chat message does NOT answer it, and an unanswered prompt expires with "Silence is not consent", which reads exactly like a refusal. So trigger the write and then tell the user the ONE human action needed (accept the prompt when it appears) — never report the file as uneditable. Do not route around the guard via `terminal`/`execute_code`. Two mechanics: a blocked attempt CLEARS this task's read-state of that file, so an immediate retry is refused as `stale_write_blocked` — `read_file` the target again, then re-issue the SAME write — and if no prompt can be answered at all, hand the user the exact replacement text in a fenced block to paste. When `AGENTS.md` carries a fact a change just made staler (a suite count, a stage list), correct the record in `CONTEXT.md` meanwhile: a stale line the change created and nobody flagged is worse than one handed over with a name on it.
- **A `pgrep`/`ps` wait-loop self-matches and hangs forever.** A guard written as `while pgrep -f 'bin/rails test' …` never exits, because the loop's OWN cmdline contains that pattern — the `[ ]` bracket trick hides the pattern from the matcher, not the real command text in the same cmdline. Filter shell wrappers out: `pgrep -af 'bin/rails test' | grep -vE 'bash|hermes-snap|pgrep'`. Bound the wait too (`for i in $(seq 1 24)`), and never put an unbounded self-matching guard in a subagent's brief.
- **OPEN THE TARGET VIEW FILE BEFORE THE FIRST EDIT — a request names a PAGE, and guessing which one is the single costliest mistake in this app.** The catastrophic version: the operator asked for the RUN JOB page's layout and the change was written into `pages/schema.html.erb` (the JSON page) instead, because that was the file already open in context — then deployed, then reported as done. Every round after that was damage control, and the operator's read was "I wanted the run job page with the json visible". Resolve the route with `search_files` (`new_job` → `jobs#new` → `app/views/jobs/new.html.erb`), read that file end to end, and name the EXISTING wrapper the request refers to (here: the `card card-glow` capped at `max-width:760px`, and the collapsed accordion) BEFORE the first patch. The trap is that two pages here both contain a "Run Job" block, which is exactly why the wrong one looked plausible. Opening the file first costs one call; guessing wrong costs the whole session.
- **Reverting a wrong-page edit WITHOUT throwing away approved work in the same file.** These files carry changes the operator has already accepted, so `git checkout -- <file>` destroys good work. Revert surgically: `git diff <file>` first to see exactly what the wrong edit added, remove only those hunks, then re-run `git diff` and confirm the remainder is the approved work. DELETE any test that asserted the reverted behaviour — a test pinning a layout the operator rejected is a false specification, and any harness the revert orphans goes with it. Report which file went back to which state plainly; do not summarise the round as "fixed" when half of it was undone.
- Resolve a setting in ONE place. The sweep's candidate cap was read twice — merged into the sweep config AND re-read directly in `main()` — so the second read silently won and `max_candidates: 3` produced 12 candidates. Two resolution sites for one knob cannot be proven consistent by testing either path; collapse them and keep the precedence rule in a comment at the single remaining site.
