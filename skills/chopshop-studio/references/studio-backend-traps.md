# Studio backend, runner, deploy and tooling traps

The application-side pitfalls that are not layout: the runner contract, uploads,
auth and session, deploy/asset commands, the Rails/Ruby version traps, and process
handling. Front-end and browser-probe rules are in
`layout-and-probe-pitfalls.md` and `headless-layout-probe.md`.

- **SEVERAL SESSIONS DRIVE THIS ONE CHECKOUT, so "dirty" does not mean "abandoned", and a red suite may be YOUR interference.** Answer "is anyone else working here" BEFORE running anything — `ps -eo pid,etimes,cmd | grep -E "rails test|bin/rails runner"` for a sibling run, and compare file mtimes across two observations minutes apart (a working set that GROWS is live development, not a parked handoff). Two traps follow from it, both measured on this box:
  - **The test invocation is `RAILS_ENV=test env -u PYTHONPATH PARALLEL_WORKERS=1 bin/rails test` — three flags, each load-bearing, and a bare `rake test` runs NOTHING.** This repo defines no `Rake::TestTask`, so `bundle exec rake test` exits 0 having executed zero tests, which is why a child citing "N runs, 0 failures" may have gotten that number from a different command than the one you re-ran; `bin/rails test` is the real runner. `RAILS_ENV=test` is required or the boot aborts with "Your Rails environment is running in production mode". `env -u PYTHONPATH` strips an ambient PYTHONPATH this box exports (it carries the local Jev backend's key and breaks the suite). `PARALLEL_WORKERS=1` forces serial execution, which is what keeps the single SQLite test DB from self-colliding. The tool often swallows the summary line, so redirect to a scratch log and read the counts from it: `RAILS_ENV=test env -u PYTHONPATH PARALLEL_WORKERS=1 bin/rails test > ~/.hermes/cache/scratch/rt.log 2>&1; grep -aE 'runs,|assertions' ~/.hermes/cache/scratch/rt.log`.
- **There is ONE SQLite test database, so two concurrent `bin/rails test` runs collide.** The symptom is a flood of `ActiveRecord::StatementTimeout: SQLite3::BusyException: database is locked` at `test/test_helper.rb:84` and a suite reporting thousands of errors with almost no assertions — measured 1162 runs / **1793 assertions / 962 errors** where a clean run of the same tree is 1162 runs / **11555 assertions / 0 errors**. It reads exactly like a wrecked tree and is not one. **The harm is symmetric: your run pollutes THEIRS too**, so a session that is iterating on test failures may be chasing phantoms you caused. Check for a sibling test process first, treat a concurrent run as a reason to WAIT rather than to interpret the number, and say so when you report a red suite you caused.
  - **A test that registers GLOBAL state at file-load time breaks when a sibling test clears that global — re-register in `setup`, not at the top of the file.** A rake-task test that does `load lib/tasks/foo.rake` once at load time passes in isolation and errors in the full suite with `Don't know how to build task '…'`, because a sibling test calls `Rake::Task.clear` (wiping every registered task) and, running alphabetically later, leaves the task gone by the time the task-invoking tests execute. Fix: wrap the registration in a helper and call it from `setup` so it re-registers after any such clear — make it idempotent (`unless Rake::Task.task_defined?(…)`). The same shape applies to any global a test populates at load (constants, memoized singletons). **A failure that appears only in the full suite is an ORDER/isolation defect, not a regression — reproduce it in isolation first** (`bin/rails test test/lib/the_file.rb` passing while the full run errors is the signature) before touching the code under test.
  - **A pre-existing failure can MASK a real one, and publishing/regenerating can surface it.** When one known-red check (a `sync-skills --check` drift, a count mismatch) dominates the run, a second unrelated error hides behind it and reads as part of the same noise. Fix the loud known failure first, then RE-RUN the full suite and attribute whatever new errors appear — do not assume the post-fix error set is a subset of the pre-fix one. A masked failure is still a failure; it just was not visible yet.
- **A dirty tree you did not make is not yours to land.** `docs/agents/standards.md` rule 9 — "A dirty tree you did not make is not yours to commit, stash, or copy over" — plus its pre-commit checklist item "nothing in the commit belongs to another workstream". A work order left in the checkout (e.g. a `MODELS_BRIEF_*.md` the plan doc names as a repo file) is that workstream's spec, and its fate belongs with the commit that lands the work; the workstream's own record will usually say so ("the close belongs with the commit that lands it"). Confirm the writer is STOPPED before touching anything, and never freeze a half-edited tree to satisfy an instruction to "sort it out".

- **A recurring task enqueues on `solid_queue_recurring`, which NOTHING here works — declare `queue: runs` or the task never executes.** `config/queue.yml` pins the single worker to `queues: "runs"` (one queue, one thread, the serial gatekeeper that keeps two runs off a runner), while Solid Queue's own `RecurringJob` does `queue_as :solid_queue_recurring`. The dispatch path therefore looks COMPLETE and silent: the `solid_queue_recurring_tasks` row is created (`create_or_update_all` at boot), a `solid_queue_recurring_executions` row is recorded with a `run_at`, the job is enqueued — and it then sits in `ready` forever. Nothing fails, so there is no error anywhere to find. Measured on this box: 30 ready `RecurringJob`s, 0 failed, and the hourly `clear_solid_queue_finished_jobs` had NEVER run. Diagnose with `SolidQueue::ReadyExecution.count` against `SolidQueue::Job.group(:class_name).count` — ready ≈ all recurring jobs is the signature. FIX: `queue: runs` on every entry in `config/recurring.yml`; `RecurringTask.from_configuration` reads `options[:queue]` into `queue_name` and `enqueue_options` puts it on the job. Do NOT "fix" it by adding a second worker entry for the recurring queue: the DB pool is exactly sized (`max_connections: RAILS_MAX_THREADS` = 5, with 3 Puma threads + 2 queue processes), so a third queue process over-subscribes the pool, and Solid Queue only WARNS (`warn_about_incorrectly_sized_database_pool`) rather than refusing. Purge the accumulated ready jobs before the restart — a backlog of stale sampler tasks each runs its `command` once, writing a burst of rows timestamped `Time.current`.
- **`schema.rb` must describe EVERY migration's table, or `db:test:prepare` builds a broken database.** This schema is hand-maintained (no dump after migrate), so a table added by a migration whose author forgot the schema edit exists in production and NOT in a schema-built DB. That is how `session_drafts` went missing: every `DraftHandoffTest` errored `Could not find table 'session_drafts'` while production was fine. Note the tell — `CreateSessionDrafts` is the one migration here NOT guarded with `table_exists?`, so `db:migrate` could not paper over it either. Related: `bin/rails db:migrate` CANNOT build a fresh DEVELOPMENT db at all — it aborts at `20260928000500_add_palette_to_composites` with `Could not find table 'composites'`, because `composites`/`scrapbook_items` have no create migration (schema.rb is their source). Use `db:test:prepare` for test and `RAILS_ENV=production bin/rails db:migrate` for production.

- `before_action :require_login` and `current_user` set the auth gate. A new endpoint (`/datasets/draw`, `/datasets/library`, `/datasets/surface`) is only gated if its controller carries `before_action :require_login` and its route points to that controller (`config/routes.rb`). Verify by reading controller source + routes + `RAILS_ENV=production log/production.log` (`Started GET`/`Processing by`/`Completed`), not by external `curl` — an upstream 403 from Cloudflare/nginx is different from a Rails auth redirect (`302` to `login_path`). A green `200 OK` in the Rails log is the real proof; a `302` to `/login` proves the gate fired; anything else is upstream. Always check the production DB (`RAILS_ENV=production bin/rails runner`) when querying live state — the development DB (`development.sqlite3`) is nearly empty and will contradict the GUI.

- `RunnerClient` (app/lib): NEVER add a keyword argument to `post` again without converting every
  call site to an explicit braces hash. With a keyword in the signature, a trailing bare
  `key: value` list is parsed as KEYWORDS, the positional `body` arg disappears, and every caller
  raises `ArgumentError (wrong number of arguments (given 1, expected 2))` — which surfaced as a
  500 on Proof/`create_validation` and on job dispatch/`create_job`. One signature change broke two
  call sites silently; braces at the call site are the contract.
- Runner (the real docker runner) keeps its job index in memory only; a container restart 404s
  every `/files/<job>/...` request until jobs are re-indexed from disk (`reindex_jobs()` scans
  `runner-data/jobs/*/` at boot, inserting every dir as `state: "done"` so a restart cannot
  fabricate a queued job). The mock runner is ephemeral by design — its `/tmp/chopshop-mock/` is
  wiped on reboot.
- Source-preview contract: Rails requests `source.png`; the mock runner writes
  it, the docker runner stores the source as `input/<upload>.<ext>`, and
  `artifact_path` falls back to `input/` for `source.png` ONLY — never a
  `name.startswith("source.")` prefix fallback. A prefix fallback serves the
  original upload for DERIVED names too (`source.inverse.png`), so a job with
  no prep twin shows the plain source as its own "inverse twin". Derived names
  resolve via their real prep file (`01_prepped/<stem>.prepped.inverse.png`) or
  return None and the studio tile self-hides (see the img-onerror rule in
  ui-conventions). When verifying the fix, HASH-COMPARE `source.png` against
  `source.inverse.png` (md5/sha) — the old bug served both with HTTP 200 and
  identical bytes, so two 200s is NOT proof the twin is actually inverted.
- Source uploads MUST live under `storage/uploads` (private), never
  `public/uploads` — the latter is served statically with no auth, leaking raw
  source rasters without a session. The runner bind-mount and
  `HOST_UPLOAD_ROOT` both point at `storage/uploads`; keep them in sync.
- `upload_preview/:name` route needs `format: false` (or a dot-friendly
  constraint) or `.png`/`.jpg` is split into the format segment and the action
  404s.
- Nothing in the stack auto-starts at boot: nginx and the Docker real runner (`restart` policy) come back, but production Puma on :3001 and the mock runner on :8790 do not — the public URL then serves 502 from nginx while `tailnet serve` may also report "No serve config". After any reboot run `bash ~/start-chopshop-stack.sh`, then walk the full verification gate instead of reporting the 502 as fixed.
- During outage recovery, finish repair plus live verification before sending a progress or success message. Repeated partial attempts create stale processes and misleading diagnostics.
- The validation row is created `pending` BEFORE the runner call, so any failure in between strands a phantom queued back-half run (no `runner_validation_id`, nothing on the runner side, never executes). Rescue only `RunnerClient::RunnerError` and a stray `ArgumentError` produces a phantom row per retry, which is exactly what "there are jobs queued I didn't start" looked like. The controller now also rescues `StandardError`, marks the row terminal, then re-raises. When asked to clear such a queue: attribute every row from the nginx access log (`sudo -n grep "POST /validations" /var/log/nginx/access.log` — the User-Agent separates the operator's real browser at the Cloudflare IP from local `curl`/`HeadlessChrome` verification, and a log of 500s explains the identical retries), dump the rows to JSON before touching them, then set them `error` (STATES has no `cancelled`; `error` is the terminal state) and confirm `pending`+`running` is 0.
- **Never precompile without `RAILS_ENV=production`.** A bare `bin/rails assets:precompile` succeeds, prints only `Warning: You are precompiling assets in development`, and writes digests the production `.manifest.json` does not point at — so the deploy looks clean and the served page keeps the old CSS. With the env prefix but WITHOUT sourcing `~/.chopshop-studio.env` it fails loudly with `Missing secret_key_base`; that failure is the env file, not a broken app. And an existing `public/assets/.manifest.json` from a development run is itself the reason Rails will not serve changed assets — check the manifest's `application.css` `digested_path` (top-level key, not an `assets` sub-key) against the file you just built before restarting anything.
- **A merge that lands AFTER your deploy leaves the box serving assets `main` no longer contains — recompile and restart on the MERGED tree, and read the digest back out of `.manifest.json` rather than quoting a number from prose.** The digest is hash-stamped and rotates on ANY change to the source, so a merge touching `application.css` (the one file two writers here both touch) invalidates the deployed bundle: the served page references a digest the tree no longer produces. The tell is a `.manifest.json` mtime OLDER than the newest commit touching `app/assets` — compare those two timestamps before believing a deploy is current, and assert the digest in the SERVED html matches the manifest.
- **When a concurrent agent has already merged and pushed your commit, rebase is the wrong move — verify ancestry and re-verify the auto-merged files instead.** `git merge-base --is-ancestor <you-sha> origin/main` answers whether the work is already in (a merge commit on top of it counts as in); `git rev-list --left-right --count origin/main...HEAD` then shows whether anything is left to push. Do NOT `git checkout -- <file>` or re-apply your own work to "tidy" it. What DOES need checking is the auto-merge itself: a merge that silently combines CSS or ERB from two writers can leave a duplicated rule or a doubled block, so after any concurrent merge run the suite on the merged tree YOURSELF and assert single-occurrence counts for the selectors you own (`grep -c '^\\.status-grid' app/assets/stylesheets/application.css`) — a clean merge exit proves nothing about the result.

## Filing to this repo's issue tracker

Issues go to GitHub through `gh`; the label vocabulary is `docs/agents/triage-labels.md` — read it and use those exact strings (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) rather than inventing a scale.

- **Write the body to a FILE and pass `--body-file`; never inline `--body "…"`.** An issue body is markdown full of backticks, `$`, pipes, quotes and `#` — the shell eats all of them inline, and the issue files with mangled content while `gh` still exits 0. Staging the issues in a local file (one `=== ISSUE` / `TITLE:` / `LABELS:` / `BODY:` block each) and filing from it also lets you re-run the whole batch.
- **Re-probe the credential IMMEDIATELY before declaring an access blocker — a 403 is often a lagging permission, not a wall.** A fine-grained PAT's newly granted permission propagates with delay, so a probe taken minutes earlier can be stale; and the operator may have just granted it. Confirm which account is answering (`gh api user -q .login`) and re-read the status (`gh api -i repos/<o>/<r>/issues | head -1`) in the same breath as writing the blocker. `gh issue list` (GraphQL) and `gh api` (REST) do NOT fail identically, so an error from one is not proof the other is blocked. Announcing a blocker that a one-command retry dissolves is worse than a slow start.
- **Verify AFTER filing, by listing.** Read the issues back (`gh api "repos/<o>/<r>/issues?state=all&per_page=100"`) and reconcile the per-label counts against what was filed; a create that exited 0 is not proof the body and labels landed. Read `state=all`, not just open — a CLOSED issue that already covers the ground is the answer to "should this be filed", and check the repo's own audit docs (`docs/agent-surface-gaps.md`) so a still-open item is referenced rather than re-described.
- **A tracker issue is the ACTION, not a copy of the finding.** Total silence is the signature of the faults worth filing here (a task that never runs, a deploy that silently falls behind), so say what to CHANGE and who decides — an item needing the operator (rotate a live secret) is `ready-for-human` and must say so, and nothing long-form should exist only in a home-directory handoff file where nobody reads it.
- **Cross-link each filed issue back into `CONTEXT.md` in the same pass — the pointer is what stops the finding being re-derived and re-filed later.** Filing without the pointer leaves two records that both look authoritative and neither of which is complete: the caveat reads as unfiled, so the next agent reinvestigates it and may open a duplicate. Add a short `Tracked as #N` clause at the caveat or work-in-progress bullet that already documents the fault (not a new section), place the issue's number in the tracker's own vocabulary, then commit that separately — and expect a push rejection, since this doc is shared with a concurrent writer (see the ancestry/rebase rule above).
- **A fine-grained PAT that cannot LIST org repos is not a dead token.** `gh repo list geeze` returning only the old public repos, and `gh issue create --repo geeze/chopshop-studio` answering "Could not resolve to a Repository", both happen while the SAME token reads the repo fine via `curl -H "Authorization: token $T" .../repos/geeeze/chopshop-studio` and creates issues through the REST API. Re-probe with the API before declaring an access blocker; when gh refuses on a private repo that demonstrably exists, fall back to `POST /repos/OWNER/REPO/issues` (label IDs from `GET /repos/OWNER/REPO/labels`) rather than reporting the repo as missing. Verify a create by LISTING the issues back — an exit-0 create is not proof the body and labels landed.
- Batch helper: `scripts/file-issues.py` files every block of a staged file and prints the resulting numbers; it exists so the quoting rule above is structural rather than remembered.
- **Before deleting a staged artifact as "redundant", prove the tracker's copy is BYTE-IDENTICAL — a body that arrived TRUNCATED makes the delete the only loss of the rest.** Until that comparison runs, the staging file is the only complete copy: fetch each filed body back (`gh api repos/<o>/<r>/issues/<n> -q .body`) and compare it against its staged block, requiring every one to match before `rm`. A create that exited 0, or a read-back of title and labels alone, does not prove the TAIL arrived — and a long markdown body is exactly the thing a write path can clip.
- **Clean up ONLY the files this session created; leave the rest of the scratch dir alone.** `~/.hermes/cache/scratch` and `/tmp` hold earlier sessions' and other agents' debris (probe dumps, `.bak` files, one-off images) alongside files that are LOAD-BEARING — `CONTEXT.md` names `repair_drawings.py` in that scratch dir as the repair path for a lost bp drawing. So `rm -rf` on the directory is data loss, not cleanup: delete the named files you made (staged issue lists, one-shot scripts, page dumps), check each is gone by testing for its existence, and let the scratch dir's own idle prune handle everything else. State in the report which ones you deliberately LEFT and why — the operator asked for redundancies removed, not for the directory emptied.
- An auth-gated page cannot be verified by fetching the page. `curl /json` returns **302** to the login flow, so a green `HTTP 302` plus a grep of the body proves nothing about the layout. For a change to a gated page, verify in two independent places instead: (a) fetch the DIGESTED asset by name and grep the new class/rule out of it (`curl http://127.0.0.1:3001/assets/application-<hash>.css` → 200, new selector present), and (b) render the view offline with `ApplicationController.render` and walk the DOM. Say plainly which of those you ran — do not present a 302 as a page check.
- **Do not try to script-login against production Puma to verify a gated page — production `protect_from_forgery` rejects a scripted `POST /login` with 422 even when you send the real token and session cookie**. The integration harness works only because TEST disables forgery protection; a browser works because it runs the page's own JS. Fighting urllib/curl past that 422 burns the session for nothing. The dependable paths are the two above — the digested asset (unauthenticated, carrying your selector) and the offline `ApplicationController.render` DOM walk.
- `bin/rails runner` defaults to `RAILS_ENV=development`, but the app the operator uses is production — `storage/production.sqlite3`, a DIFFERENT database with different jobs. Querying it without the prefix shows a nearly empty world while the GUI lists jobs the runner never heard of, which reads as a contradiction instead of a mistake. Always `RAILS_ENV=production bin/rails runner` for anything about live state, and print `ActiveRecord::Base.connection_db_config.database` to prove which file answered. The `prod` DB is also multi-database (`primary`/`cache`/`queue`).
- **A recorded suite BASELINE is environment-specific — re-measure it on the box you are on, and rewrite the number in place when it disagrees.** A baseline of "1 failure + 10 errors + 6 skips" was recorded for this repo from a `chopshop-app` CONTAINER, and this box has no such container (the app runs as the `chopshop-rails.service` systemd USER unit; the only container present is the pipeline runner, publishing `127.0.0.1:8787`). Measured on the host the same suite is fully green, so that figure is a FALSE SPECIFICATION: it tells the next agent to expect noise, and a genuine failure then hides inside the expectation — which is worse than having no baseline at all. Both of its causes are path/provisioning differences, not code, and both are worth knowing so a red test is not misread as the old noise: the JEV tests resolve the annotator as `Rails.root.parent.join("chopshop-jev/scripts/…")`, which is `~/chopshop-jev` from a checkout at `~/chopshop-studio` and `/chopshop-jev` from one at the filesystem root; and the JSON-injection test shells out to `node --check`, which exists on this box. So run the full suite here before trusting any count written in a doc, and CORRECT the doc in place rather than annotating under it — and never carry a container-era workaround (copying the annotator into a mount) onto the host.
- **When the tree is expected to be red (a branch baseline with pre-existing failures), verify by DIFFING the failure LIST, not by expecting green.** Record the baseline on the tree WITHOUT your changes (stash or checkout the base commit, run the suite, capture the failing test names), re-run after your changes, and require the two lists to be identical — the runs/failures/errors triple alone can hide a swapped failure, and a list identical to baseline is proof a change regressed nothing even when the suite stays red. This is also how you verify another writer's claim of "suite unchanged" on a shared branch: same technique, no trust required.
- **A failure you have LABELLED "pre-existing" is a CLAIM, not a fact — re-derive it the moment you touch what the test covers.** "The N known failures" gets repeated forward session to session and stops being read, so a genuine REGRESSION hides inside the expectation and gets reported as noise. Two of three failures carried as "pre-existing skill-copy drift" were exactly that: a commit that rewrote the skill file had DELETED sentences the test asserts, and the test was right. Ask the cheap question every time — did the text the assertion names EVER exist? `git show <sha>~1:<path> | grep -c '<phrase from the assertion>'` against `git show HEAD:<path> | grep -c …` splits "never worked" from "was dropped" in one command; a phrase present at `<sha>~1` and gone now is a regression to RESTORE, not noise to tolerate. Restore it at the SOURCE, never by editing the copy the test reads.
- **When the failing check is "generated output is in sync", the fix is to RUN THE GENERATOR, not to edit the generated file.** A `--check` mode that compares a generated tree against its source fails the moment the source moves on, so publishing is the repair — and it is also the moment where real drift (a sentence a rewrite dropped) becomes visible. Do not "fix" the generated copy to make `--check` green: it is downstream by construction, and a hand edit there is silently overwritten by the next publish.
- Minitest here is 6.x, which DROPPED `minitest/mock` — `Object#stub` does not exist and `require "minitest/mock"` is a LoadError. Stub by hand: save `RunnerClient.method(:create_validation)`, `define_singleton_method` the replacement, `ensure` restores it. Integration controllers also need a modern `User-Agent` header or `allow_browser versions: :modern` returns 406, and the login gate is satisfiable in-test by POSTing `login_path` with the seeded `test`/`test-password` user (`test_helper.rb` seeds it and sets `Current.user_handle = "test"`, so no env var to restore).
- **Making a field REQUIRED on a create path breaks every posting test in the tree — fix them with ONE shared factory, and normalize sentinel values before any `blank?` guard.** When the Run Job create action began refusing project-less HTML posts, the new test file was green while dozens of existing tests across a dozen files failed — all in files nobody had touched. Procedure: (1) put a memoized factory in `test/test_helper.rb` (`@thing ||= Model.create!(name: "probe-#{rand(1_000_000)}")` — random suffix so classes never collide; the per-test transaction rolls it back); (2) `grep -rn 'post <route>' test/` and add the field at EVERY post site, counting the sites against the grep total before re-running; (3) re-run the FULL suite — form posts fail in files you did not edit, so touched-file runs lie; (4) the agent/JSON exception to the new rule gets its own pinning test plus a `docs/agent-api.md` row stating both halves. **The Rails trap alongside it:** a non-integer sentinel (`"__new__"`) on an integer attribute is cast by Rails to `0`, so `blank?`/`nil?` are both false and a "treat as omitted" guard silently passes `0` through — the record then files under an id that does not exist and is listed nowhere. Normalize with `param.to_i <= 0 → nil` BEFORE any blank check, and pin it with a test that posts the sentinel.
- **Native gems won't build under `bundle install` here — `/var/lib/gems/3.2.0` is root-owned.** A gem with a C extension (bcrypt) fails its native build during `bundle install` because it must write into a system dir owned by root, not because of the gem itself. Uncommenting the gem in the Gemfile is not enough — the native build is what fails. Fix: `sudo -n gem install <name> -v <version>` first (installs system-wide as root), then `bundle install` completes against the already-installed gem. No `.bundle/config` path override exists on this box, so sudo is the fix, not a workaround.
- **Production Rails does not hot-reload, so a Puma started mid-deploy serves stale code.** A process booted between two of a feature's file writes (Puma at 03:26, `flux_conf.rb`/`flux.html.erb`/`jobs/new.html.erb` at 03:27, `job.rb` at 03:56) 500'd `/jobs/new` and `/flux` on `uninitialized constant FluxConf::PLACEMENT` / `undefined method runner_kind` — code that was already in the tree and green in the suite. Symptom = 500 on a NEW route/constant; fix = `systemctl --user restart chopshop-rails.service`, not the code. Restart after any pull or `app/`/`config/` edit, and verify the served page before reporting done.
- Stop a service by PID, not `pkill -f <pattern>`: if the pattern string also appears in your own command line, pkill matches the shell itself and SIGTERMs it, leaving the target alive. The same self-match fires inside a WAIT loop (`for i in $(seq 1 40); do pgrep -f 'pytest tests/' >/dev/null || break; ...`) — it matches its OWN command line, never breaks, burns its full budget, and reports "STILL RUNNING" for a suite that finished minutes earlier. Resolve the PID from `ss -ltnp` or a separate `ps -eo pid,args | grep` call, kill by number, then confirm the port is free. Match the interpreter and module you actually mean (`.venv/bin/python -m pytest`), or take the result from the background process's own completion notification rather than polling a pattern you are also typing.
- **The fuzzy `patch` matcher corrupts tokens in ERB, Ruby and test files — verify every edit, and use an exact replace for fragile one-token changes.** Its fuzzy match merges NEIGHBOURING text instead of replacing exactly, so a closing block was rewritten as `endnd`, a constant came back self-referenced as `NAME_SLUG_KEYSLUG_KEY`, and a test string as `comomposite` — every one compiling or running as far as the shell knew, wrong in the file. After any non-trivial edit run the syntax check (`ruby -c` for Ruby; the `ERB.new(...).src` compile) AND read the hunk back. For a one-token change, prefer `execute_code` with an exact `old in src`-guarded `src.replace(old, new)` over the fuzzy matcher; anchor the `old_string` on a unique coordinate that includes the surrounding token (a bare `end` or a bare constant matches the wrong occurrence).
- **The `terminal` tool expands IP-placeholder tokens in commands into invalid values, breaking every URL test that contains an IP address.** When a command contains an IP placeholder, the tool substitutes a value that corrupts the URL. Symptom: every connectivity test fails with a URL-parsing error, even though the same URL works when typed into a Python script or read from a file. **Fix: write the test to a file first and execute it, or use Python with hardcoded IPs — never type IP addresses directly into terminal commands.** This cost a full session diagnosing phantom failures that were tool artifacts, not real connectivity problems.
- **Propshaft does not minify or strip comments — nothing redacts them for you.** This app ships on Propshaft (1.3.x) with `config.assets.js_compressor`/`css_compressor` left nil by the railtie and no terser/cssnano/esbuild pass, so every `//` and `/* */` comment in `app/assets` and `app/javascript` reaches the browser verbatim in the digested bundle. To redact at precompile, register a custom compiler: `config.assets.compilers += [["text/javascript", Stripper], ["text/css", CssStripper]]` where the class inherits `Propshaft::Compiler` and implements `compile(asset, input)` returning the rewritten String. `config.assets.compilers` is an array of `[mime_type, klass]` pairs defaulting to `CssAssetUrls`/`JsAssetUrls`/`SourceMappingUrls` — APPEND, never replace, or the URL-rewrite compilers stop running.
- **Naive `//`-stripping corrupts real code — guard `://` and regex literals first.** A raw "delete from `//` to EOL" pass also eats `https://` inside strings/comments (`application.js:1`) and `/…/g` regex literals (`aether.js` has `.replace(/&/g, …)`, `.replace(/[&<>"']/g, …)`), silently breaking the module. Strip block + line comments with a tokenizer that skips `'`/`` ` ``/`"` string bodies and `/…/` regex bodies, and run `node --check` on every touched file before and after the pass to prove nothing changed semantics.
- **The login page serves the ENTIRE site bundle — `javascript_importmap_tags` in the layout head is unconditional.** `import "application"` → `import "aether"` pulls the whole 2,100-line `aether.js` IIFE (scrapbook, candidate/proof viewer, preview toolbox, magnetic hover, running-job polling, Jev cards, popup wiring) onto the password page. The login inline script uses only TWO things from it: `window.CsModal` (password gate + triple-click tuning) and `ensureBackground()`'s `.orb-3` node (which `pinCentralOrb()`'s MutationObserver waits on). Slim it by gating the importmap ENTRY on auth — a dedicated login entry (modal + background only) when `current_user` is nil, the full `application` entry otherwise — never by deleting feature code out of `aether.js`, which every authed page shares.

## Auditing a reference page against the service it documents

The reference pages (`/bp`, `/flux`, `/jev`, `/status`) transcribe an EXTERNAL
service's contract, so they can be wrong in a way no suite catches: the page's
copies of the constants are compared against nothing, and the service is a
different process on a different host. Audit it this way.

**Diff the page against the service's real code, not against its docs.** Read
the service's validators and defaults directly (`~/chopshop-bp/chopshop_plot/`
for the blend-plot half). Two live defects were invisible from reading the page
alone: it emitted an env var the service has never heard of (so a
token-protected deployment would 401 on every render), and its "Checks" card
called an empty `elements` list legal when the service refuses it without a
`tiling` block. Neither is findable by reading the page — both need the
service's source.

**A page that documents a service must also show what the CLIENT submits.** The
audit's biggest finding was an omission, not an error: the page carried the
element tables, chart lists, defaults and routes, and no job spec for ANY
operation, so nothing on it could be pasted into Run Job. When auditing, ask
"can I copy something from here and have it run?" per operation, and answer it
for every one.

**Take the examples from the service's own fixtures, and RE-RUN them through the
service's own validators before publishing.** `~/chopshop-bp/examples/*.json`
are what its README points at and its tests accept. Import them into a model
(`BpExamples`) and show them with the source filename as provenance, so a reader
can re-verify when the service changes. Hand-written plausible specs are the
trap: a first attempt at eight of them was refused in three separate ways, and a
plausible-looking spec proves only that its author was confident.

**A "Checks" card is a SUBSET of the contract, and the subset is the bug.** A
three-rule validator (elements is an array / views is a positive integer /
engine is known) reads as a contract while accepting bodies the service
rejects — unknown element types, unknown fields on a known element, non-numeric
coordinates, a `views` select that contradicts the document's own `render.views`.
Whenever one page control validates less than the service does, say so on the
page rather than letting it read as authoritative.

**Derived-page checks are still server-side, not client-side.** Where a page
computes a verdict in JS, the Ruby twin must exist and a test must assert the
TWO AGREE — a card that says "legal" in the server-rendered copy and "refused"
after the script runs is a card that lies twice, and the divergence only shows
up in a browser.
